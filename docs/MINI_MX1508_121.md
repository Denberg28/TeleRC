# Mini rover 1.2.1 — MX1508 no-movement review

Keep TeleRC **0.8.56** and its full interface. Upload the updated `TeleRC_MiniRover_WiFi` sketch and keep all headers together. This is firmware-only; no APK replacement is required. Default: ESP32-S3, four individual motors, two MX1508 boards, SSID **TeleRC-MiniRover**, password **telerc123**, UDP 14550.

## Findings and changes

The user's GPIO mapping already matches the firmware. There is no verified pin-number defect.

A reproducible range mismatch was found: the APK produces 1100–1900 µs at 100% sensitivity; firmware 1.2.0 normalized against 1000–2000 µs. Its nominal straight-drive maximum was therefore only **142/255**, below the configured **180/255** limit. Version 1.2.1 maps 1100/1900 to full normalized demand, retains neutral 1500 and deadband ±25, and clamps wider valid commands. It reaches the existing 180 limit without introducing a minimum-duty boost or increasing that limit. With app sensitivity 25%, full straight drive remains only 36/255 and may be below a motor's starting torque; use 100% for the raised-wheel diagnosis.

The output layer also ignored failed LEDC writes. Core 3 PWM writes are now checked; any detected failure detaches PWM, drives all configured outputs low, disarms, and rejects further ARM until reboot. Serial diagnostics report command freshness, CH1/CH2, commanded motor duty and LEDC register readback. Readback is not a GPIO voltage, motor-speed or power-supply measurement. Core 2's void write API does not offer equivalent runtime error detection; pinned target builds use core 3.3.2.

The MX1508 default PWM is now **1 kHz**, giving longer pulses for bench testing with small brushed motors. Other driver profiles retain their previous frequency defaults. The previous 20 kHz setting has not been proven to be the cause on the user's hardware. Power, grounding, actual GPIO waveforms, motor friction and driver condition still need physical verification. This package is a test candidate, not a confirmed physical repair.

## Exact wiring

| Motor | Driver input | ESP32-S3 GPIO |
| --- | --- | --- |
| Left front | Driver 1 IN1 / IN2 | 4 / 5 |
| Left rear | Driver 1 IN3 / IN4 | 6 / 7 |
| Right front | Driver 2 IN1 / IN2 | 8 / 9 |
| Right rear | Driver 2 IN3 / IN4 | 10 / 11 |

**Required power wiring:** ESP32 GND, Driver 1 GND, Driver 2 GND and motor-supply negative must join. Supply both driver power inputs from a suitable motor source (default profile declares at most 5 V and 6 V-rated motors). Power the ESP32 from regulated logic power. The eight control wires alone do not power the motors. Do not power motors from the ESP32 3.3 V pin. Connect each motor to its matching driver output pair.

## Upload and raised-wheel test

1. Remove motor power during upload. Arduino IDE: esp32 by Espressif **3.3.2**, **ESP32S3 Dev Module**, **USB CDC On Boot Enabled**. Open the .ino with all its headers. Use the existing 4/5, 6/7, 8/9, 10/11 wiring; no remap is required.
2. Raise wheels, keep an independent motor-power cutoff accessible, connect driver power and common grounds. Open Serial Monitor **115200 baud**. Confirm periodic `v=1.2.1-mx1508-diagnostics drv=MX1508 hz=1000`.
3. In TeleRC Setup set sensitivity to **100%** for this test. Select **Mini rover Wi-Fi**, Connect → Controls → Enable Control → center until ARM ready → ARM. Wait for the button to show **DISARM / rover ARMED**; command ACCEPTED alone is not the final armed-state confirmation.
4. Hold a forward drive command with steering centered. `CH2` must rise above 1525 (toward 1900), `arm=1`, `move` must increase, and OUT/PWM must become nonzero for all four motors. At full forward the default expected values are `OUT=180/180/180/180` and `PWM=180,0/180,0/180,0/180,0`. Do not begin with a low-sensitivity steering-only test.
5. Release: CH2 returns to 1500 and all outputs become zero. Verify DISARM, STOP, tab/background, Wi-Fi loss and local BOOT stop. After a fault/reboot/reconnect, centering and explicit ARM are required again. Measure output-zero timing separately from mechanical coast distance.

## Interpret one line while holding forward

| Observation | Meaning / next check |
| --- | --- |
| `arm=0` | Arming not retained; check `reason` and fresh RC. Reconnect, Enable, center, then ARM. |
| `rc` not increasing or `reason=COMMAND_TIMEOUT` | Motor commands are not fresh. Verify Enable Control, active Controls tab and Wi-Fi link. Discovery/ARM replies do not feed the drive watchdog. |
| `CH1=1500 CH2=1500`, move unchanged | App is sending neutral; check joystick/channel feedback, Enable and input. |
| Low nonzero OUT, e.g. 36 | Low effective command; set app sensitivity 100% for raised-wheel testing. There is no forced minimum PWM. |
| `ready=0 err>0 reason=PWM_ERROR` | PWM API failure detected. Outputs are latched off. Preserve the line, remove motor power and reboot; repeated failures need board/core/peripheral investigation. |
| `arm=1`, OUT and PWM nonzero, motors still stationary | The command/software duty path is active. Verify real GPIO waveforms, common ground, driver supply under command, correct output pair and motor/driver condition. Register readback cannot prove those. |

If movement still fails, preserve **one centered/armed line and one line while holding forward**. These distinguish an app-neutral/control issue from PWM API, power or output-stage problems; do not guess from ACCEPTED alone.

## Verification and limits

Regression tests reproduce the old full-range shortfall, assert 180 on GPIO 4/6/8/10 and zero on 5/7/9/11 at full forward, test 25% input scaling, all directions/stop/watchdog/rearm rules, clock rollover, corrupt packets, serial backpressure and injected PWM-write failure. Twenty driver/count/API host combinations and six actual core 3.3.2 target configurations are required by the release workflow. Android 0.8.56 is unchanged; its unit/lint/build/signer/protocol evidence remains run 38696307553. Hardware evidence remains pending.
